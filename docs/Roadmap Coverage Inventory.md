# Roadmap Coverage Inventory

## 1. Authority

- **Roadmap:** `docs/FedORBIT_Roadmap.md`
- **Repository:** `naslouby-salahe/FedORBIT`
- The roadmap is authoritative and immutable. This inventory is traceability state only and does not amend, weaken, reinterpret, or extend it.

## 2. Inventory Rules

1. Each row is an independently verifiable roadmap contract.
2. Exact roadmap sections/subsections remain the source of truth for all values and procedural detail referenced by a row.
3. Positive implementation obligations, negative requirements, exclusions, assumptions, terminology, claim boundaries, lifecycle rules, and failure semantics are all retained.
4. `REQ-*` identifiers become immutable once referenced by a GitHub issue; later discoveries append identifiers.
5. `Coverage` records actual downstream planning ownership, not intended future ownership.
6. `Readiness` is `READY`, `AMBIGUOUS`, or `BLOCKED` based only on whether implementation would otherwise have to invent a material decision.
7. Acceptance evidence must be objective and roadmap-derived.
8. Any disagreement is resolved in authority order: Roadmap → this inventory → milestones → issues → audit issues.

## 3. Classification

### Coverage

- `MAPPED` — owned by concrete GitHub implementation issue(s) and an owning milestone.
- `UNMAPPED` — implementation-bearing requirement not yet owned by concrete GitHub planning state.
- `NON_IMPLEMENTATION` — authoritative scope/assumption/claim constraint that does not independently require an implementation work item.

### Readiness

- `READY` — executable without inventing a material decision.
- `AMBIGUOUS` — roadmap text contains a material contradiction or unresolved interpretation.
- `BLOCKED` — an external prerequisite/material decision prevents implementation.

### Requirement Types

`Architecture`, `Algorithm`, `Mathematics`, `Configuration`, `Dataset`, `Preprocessing`, `Training`, `Experiment`, `Comparator`, `Ablation`, `Metric`, `Statistical Analysis`, `Artifact`, `Reporting`, `Provenance`, `Reproducibility`, `CLI`, `Testing`, `Validation`, `Failure Semantics`, `Idempotence`, `Claim Boundary`.
